# Миграции схемы БД

Применяются скриптом [`scripts/db/apply-migrations.sh`](../../scripts/db/apply-migrations.sh)
(он же `npm run migrate:db`). Учёт применённого — в таблице `public.schema_migrations`
(`filename`, `checksum`, `applied_at`). Миграция и запись в журнал выполняются **в одной
транзакции**, поэтому состояния «применилось, но не записалось» не бывает.

```bash
npm run migrate:db:status                                    # что применено, что ждёт
bash scripts/db/apply-migrations.sh --env-file server/.env   # применить
```

## Именование

```
YYYYMMDDHHMM_краткое_описание.sql
202607301430_add_report_comment.sql
```

Файлы применяются по алфавиту (`LC_ALL=C`), поэтому алфавитный порядок = хронологический.

## Правила

1. **Миграции неизменяемы.** Применённый файл менять нельзя — скрипт хранит его
   `sha256` и остановится при расхождении. Нужна правка → новый файл.
2. **Никаких `BEGIN`/`COMMIT` внутри файла** — транзакцией управляет psql
   (`--single-transaction`).
3. **Не класть сюда `database/stroyfoto.schema.sql`.** Это информационный снапшот
   (`npm run db:schema:pull`), а не исполняемый скрипт: в нём UNIQUE-constraint'ы
   дублируются одноимёнными `CREATE UNIQUE INDEX`, а триггеры объявлены раньше функции,
   которую вызывают — на пустой БД он падает. Роль «начального состояния» играет
   `000000000000_baseline.sql`, снятый через `pg_dump --schema-only`.

## Baseline

`000000000000_baseline.sql` — слепок схемы на момент заведения миграций.

- На **существующей** БД (прод) он один раз отмечается применённым без выполнения:
  `--mark-applied 000000000000_baseline.sql`.
- На **пустой** БД применяется обычным прогоном, дальше идут остальные файлы.

Снимать baseline нужно `pg_dump` версии **не ниже сервера** (Yandex MDB — PostgreSQL 17).

> ⚠️ Не подключайте `server/.env` через `. server/.env` или `source`: shell **исполнит**
> содержимое файла, а не просто прочитает переменные. Достаточно `grep`-выборки нужных
> ключей. Сам мигратор безопасен — `--env-file` разбирает dotenv, а не сорсит.

Слепок снимается **во временный файл** и переносится в `db/migrations/` только после
проверки: пустой или оборванный baseline, попавший в каталог, будет применён как есть.

```bash
db_url="$(grep -E '^DATABASE_URL=' server/.env | tail -n1 | cut -d= -f2-)"
ca="$(grep -E '^PGSSLROOTCERT=' server/.env | tail -n1 | cut -d= -f2-)"
tmp="$(mktemp)"

docker run --rm -v "$ca:/ca.crt:ro" -e PGSSLROOTCERT=/ca.crt postgres:17 \
  pg_dump --schema-only --no-owner --no-privileges \
          --exclude-table=public.schema_migrations "$db_url" \
  > "$tmp"

# Проверка: непустой файл и он восстанавливается в чистую PostgreSQL 17.
[ -s "$tmp" ] || { echo 'baseline пуст — не переносим'; exit 1; }

mv "$tmp" db/migrations/000000000000_baseline.sql
```

Репетиция перед продом — не только восстановление baseline: добавьте в чистую БД несколько
тестовых `reports`, прогоните остальные миграции **настоящим мигратором** (`apply-migrations.sh`,
а не вручную через psql) и убедитесь, что отработали и backfill, и триггеры.

## Разрушающие изменения: expand / contract

Удаление или переименование колонки **нельзя** катать одной миграцией перед деплоем —
в момент её применения старый API ещё работает и сломается. Порядок:

1. **expand** — добавить новую совместимую структуру (колонку, таблицу), старую не трогать;
2. выкатить API, который умеет работать с обеими версиями;
3. перенести данные (отдельная миграция);
4. **contract** — удалить старую структуру **отдельной поздней миграцией**, когда ни одна
   работающая версия API её больше не использует.

## Нетранзакционные DDL

`CREATE INDEX CONCURRENTLY`, `ALTER TYPE ... ADD VALUE` и подобное **не может** выполняться
внутри транзакции, а скрипт всегда оборачивает файл в неё — обычный прогон на таком файле
упадёт. Порядок строго ручной:

```bash
# 1. выполнить вручную
psql "$DATABASE_URL" --set ON_ERROR_STOP=1 -f db/migrations/202607301500_concurrent_idx.sql
# 2. убедиться, что индекс валиден (indisvalid = true)
# 3. только теперь отметить в журнале
bash scripts/db/apply-migrations.sh --env-file server/.env \
     --mark-applied 202607301500_concurrent_idx.sql
```

## Порядок относительно деплоя

Миграции применяются **до** выкладки кода. [`scripts/deploy.sh`](../../scripts/deploy.sh)
проверяет, не приехали ли новые файлы в этом каталоге, и останавливается с инструкцией,
если да. После применения деплой продолжают флагом `--ack-migrations-applied`.

После изменения схемы обновить информационный снапшот и закоммитить его:

```bash
npm run db:schema:pull   # перегенерирует database/stroyfoto.schema.{sql,json,md}
```
